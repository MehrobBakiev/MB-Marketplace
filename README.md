# Marketplace Architecture

## Стек

- Go 1.23
- Docker
- Docker Compose
- REST API
- C4 Container Diagram
- Kafka (архитектурный компонент для событий)

## Архитектура

Используется микросервисная архитектура с выделением доменов.

Архитектура разделяет систему на независимые сервисы, каждый из которых отвечает за свой домен и владеет собственными данными.

## Домены и ответственность

### User Domain

Сервис:
- User Service

Ответственность:
- пользователи
- продавцы
- роли
- пользовательские данные


### Catalog Domain

Сервис:
- Catalog Service

Ответственность:
- товары
- категории
- характеристики товаров


### Order Domain

Сервис:
- Order Service

Ответственность:
- заказы
- статусы заказов
- история заказов


### Payment Domain

Сервис:
- Payment Service

Ответственность:
- платежные операции
- транзакции
- статусы оплаты


### Notification Domain

Сервис:
- Notification Service

Ответственность:
- отправка уведомлений
- обработка событий изменения статусов


### Recommendation Domain

Сервис:
- Recommendation Service

Ответственность:
- персональная выдача товаров
- хранение пользовательских предпочтений


## Владение данными

Каждый сервис владеет своей базой данных.

Общих баз данных между сервисами нет.

| Сервис | База данных | Ответственность |
|---|---|---|
| User Service | User DB PostgreSQL | пользователи и роли |
| Catalog Service | Catalog DB PostgreSQL | товары и категории |
| Order Service | Order DB PostgreSQL | заказы |
| Payment Service | Payment DB PostgreSQL | платежи |
| Notification Service | Notification DB PostgreSQL | уведомления |
| Recommendation Service | Recommendation DB PostgreSQL | рекомендации |


## Взаимодействие сервисов

### Синхронное взаимодействие

REST:

- API Gateway -> User Service
- API Gateway -> Catalog Service
- API Gateway -> Order Service
- API Gateway -> Payment Service
- API Gateway -> Recommendation Service


### Асинхронное взаимодействие

Для передачи событий используется Kafka.

Примеры событий:

- Order Service -> Kafka -> Notification Service
- Payment Service -> Kafka -> Notification Service
- User Service -> Kafka -> Recommendation Service
- Catalog Service -> Kafka -> Recommendation Service
- Order Service -> Kafka -> Recommendation Service


## Архитектурные решения

### Почему выбран микросервисный подход

Плюсы:

- независимое масштабирование сервисов;
- изоляция отказов отдельных компонентов;
- возможность раздельной разработки доменов разными командами.


Минусы:

- усложнение инфраструктуры;
- необходимость мониторинга сервисов;
- сложность распределенной отладки.


Микросервисный подход выбран, так как маркетплейс состоит из независимых доменов с разной нагрузкой и требованиями к развитию.


## Альтернативные варианты архитектуры


## Вариант 1. Модульный монолит

Все домены находятся в одном приложении, но разделены на внутренние модули.

Плюсы:

- простота разработки;
- меньше инфраструктурных компонентов;
- проще тестирование.


Минусы:

- сложнее масштабирование отдельных частей;
- сильная связанность модулей.


## Вариант 2. Микросервисная архитектура

Каждый домен реализован отдельным сервисом.

Плюсы:

- независимое масштабирование;
- разделение ответственности;
- разные команды могут работать независимо.


Минусы:

- сложность взаимодействия сервисов;
- необходимость DevOps инфраструктуры;
- сложнее диагностика ошибок.


## Финальный выбор

Выбрана микросервисная архитектура.

Причины:

- маркетплейс содержит независимые домены;
- разные сервисы имеют разную нагрузку;
- рекомендации можно развивать отдельно;
- отдельное владение данными снижает связанность системы.
